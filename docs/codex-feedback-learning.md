# Codex 反馈学习机制

版本：v0.1  
更新日期：2026-06-23

## 1. 目标

本机制用于让 Codex 在本项目中持续吸收开发结果、自动检查结果和人工体验评价，并把这些反馈转化为下一轮开发的优先级、验收重点和测试覆盖。

这里的“学习”不是训练 Codex 的模型权重，也不是让 Codex 在仓库外保存隐藏记忆。项目只承认写入仓库的规则、日志、测试和检查脚本。Codex 每次工作时必须读取这些文件，并基于其中的反馈调整开发和验收策略。

## 2. 数据来源

可记录的反馈来源包括：

1. Codex 开发过程中的自动检查结果。
2. 云函数、页面流程、数据一致性或权限问题的修复记录。
3. 人工只体验最终产品后给出的评价。
4. 人工体验时发现的阻断、困惑、误操作、性能慢、流程不顺等问题。
5. 审核风险、文案风险或产品定位偏离。
6. 已通过验证且体验正向的操作流程。

人工不需要检查代码。人工反馈应尽量描述“用户做了什么、看到什么、哪里不符合预期、影响多大”。

## 3. 反馈记录位置

反馈统一记录在：

```text
docs/codex-feedback-log.md
```

每条反馈必须尽量包含：

```text
日期
来源：auto | human | codex
场景：创建房间 / 加入房间 / 单人记分 / 批量记分 / 转移 / 撤销 / 关闭房间 / 分享 / 记录查看 / 其他
结果：positive | negative
分值：正数表示加分，负数表示扣分
严重度：1 到 5
置信度：1 到 5
影响模块：miniprogram / scoreFunctions / docs / config / unknown
关联代码位置：文件路径、页面、函数、样式类或配置项
问题对应关系：反馈问题分别对应哪些代码位置或规则
现象
根因或推测
处理方式
是否需要新增自动检查或测试
```

如果根因无法确认，必须标记为“待确认”，不能编造。

关联代码位置必须具体到可操作对象，例如：

```text
miniprogram/pages/index/index.wxss：`.primary-button`、`.secondary-button`、`.ghost-button`
cloudfunctions/scoreFunctions/index.js：`transferScore`、`assertTransferPermission`
miniprogram/app.json：页面注册顺序和 `pages/create-room/index`
```

当一次反馈包含多个问题时，必须用“问题对应关系”拆开记录，避免后续只知道扣分原因却无法定位代码。

## 4. 权重评估

Codex 在规划下一轮开发时，应按以下优先级处理反馈：

```text
权重 = |分值| * 严重度 * 复现次数系数 * 置信度
```

复现次数系数：

```text
首次出现：1
重复出现：2
连续两轮以上出现：3
```

默认解释：

1. 高扣分、高严重度、高置信度的问题必须优先修复。
2. 重复出现的问题必须转化为自动检查、测试用例或更明确的规则。
3. 高加分反馈可以作为保留体验的约束，后续改动不能破坏。
4. 低置信度反馈不能直接推翻架构规则，只能作为调查线索。

## 5. 正确与错误操作的归类

Codex 应把反馈按“场景 + 操作类型 + 结果”归类。

示例：

```text
场景：单人记分
操作：房主给成员加分
正确表现：分数增加、记录写入、成员刷新后结果一致
错误表现：分数未变化、记录缺失、非房主可操作、提示不清楚
```

后续开发前，Codex 必须查看同类场景过去是否出现过扣分反馈。如果出现过，相关代码改动必须重点验证该场景。

## 6. 与测试覆盖的关系

每条负向反馈都必须判断是否能自动化：

1. 能通过命令行验证的，优先增加脚本、单元测试或静态检查。
2. 只能在微信开发者工具中验证的，写入人工验收清单。
3. 如果属于用户体验问题，记录可观察的验收标准，例如“用户不需要返回首页即可继续完成操作”。
4. 如果属于文案或审核风险，加入文案检查或项目规则。

当同类负向反馈重复出现时，必须提高自动化优先级，不能长期依赖人工记忆。

### 6.1 覆盖矩阵

Codex 每次改动时应维护以下覆盖关系：

| 场景 | 自动检查优先级 | 人工体验验收 |
| --- | --- | --- |
| 创建房间 | 云函数入参校验、房间字段、房主成员写入 | 能创建并进入房间 |
| 加入房间 | 房间码、人数上限、关闭和过期校验 | 输入房间码和分享路径都能加入 |
| 单人记分 | 房主权限、分值校验、成员分数、记录写入 | 房主可加减分，成员不可操作 |
| 批量记分 | 成员归属、批量明细、记录写入 | 多成员同时加减分结果正确 |
| 积分转移 | 事务一致性、公共积分不足校验、记录写入 | 公共积分、成员积分、成员之间转移结果正确 |
| 撤销 | 可撤销类型、重复撤销限制、反向记录 | 指定积分变更可撤销 |
| 关闭房间 | 房主权限、状态变更、关闭后禁止修改 | 关闭后不能继续记分 |
| 记录查看 | 记录类型、对象、分值、撤销状态 | 用户能理解积分流向和最近操作 |
| 分享 | 分享路径参数、加入流程衔接 | 分享入口能带用户进入正确房间 |

如果当前仓库还没有某一类自动测试，Codex 必须在验收总结中说明“当前只能通过人工体验覆盖”，并在重复扣分时优先补自动化能力。

## 7. 每轮开发使用方式

每次非简单变更前，Codex 必须：

1. 阅读 `AGENTS.md`。
2. 阅读与任务相关的需求文档和架构文档。
3. 阅读 `docs/codex-workflow.md`。
4. 阅读 `docs/codex-feedback-learning.md`。
5. 阅读 `docs/codex-feedback-log.md` 中与本次任务相关的条目。
6. 根据高权重负向反馈列出本轮重点风险。

每次非简单变更后，Codex 必须：

1. 运行项目要求的可用检查。
2. 说明哪些历史反馈已被覆盖。
3. 如有新反馈或新风险，更新 `docs/codex-feedback-log.md`。
4. 如行为、数据结构、页面流程、部署方式或约束变化，同步更新需求或架构文档。

## 8. 边界

1. Codex 不能声称已经完成真实模型训练。
2. Codex 不能把未写入仓库的历史对话当作稳定项目规则。
3. Codex 不能用统计权重覆盖硬性架构规则和产品合规边界。
4. Codex 不能因为某个流程获得正向反馈，就跳过权限、记录、事务性或文案检查。
5. 用户只负责最终体验和评价时，Codex 仍然必须自己完成代码阅读、实现、自动检查和可说明的验收总结。
