# 房间同步设计：监听当前房间文档

版本：v1.0
日期：2026-06-26
状态：两表架构同步方案

## 1. 决策

房间同步只使用 CloudBase 数据库 `watch()` 监听当前房间文档：

```text
rooms/{roomId}
```

原则：

1. 写操作只走 `scoreFunctions`。
2. `rooms` 是房间事实源。
3. 成员、公共积分、最近记录都从同一个 room 文档派生。
4. 客户端监听只用于展示同步，不直接写云端数据。
5. 不再维护额外同步表或房间读模型。

## 2. 页面流程

进入房间页：

```text
onLoad
  -> getRoom 初次加载权威数据
  -> watch rooms 当前房间文档
```

写操作成功：

```text
scoreFunctions 返回 roomView
  -> 操作端立即 applyRoomViewData
  -> 其他在线端等待 rooms watcher 推送
```

离开房间页：

```text
onHide / onUnload
  -> watcher.close()
```

重新显示页面：

```text
onShow
  -> 如果已有房间数据，则重新建立 rooms watcher
```

## 3. 更新规则

收到 `rooms/{roomId}` 快照后：

1. 更新房间基础信息。
2. 从 `room.members` 派生成员列表、待确认列表、本人状态和权限。
3. 从 `room.records` 派生最近记录，并按 `sequence` 倒序展示。
4. 保留当前弹窗、选择模式和分页状态，避免无关交互被重置。

## 4. 异常处理

监听异常时：

1. 页面保留当前展示。
2. 显示同步状态提示。
3. 静默调用一次 `getRoom` 兜底。
4. 用户下拉刷新时也可重新调用 `getRoom`。

如果线上集合权限阻止客户端读取 `rooms`，`getRoom` 仍可通过云函数返回数据，但实时同步会失败，需要调整云数据库读权限。

## 5. 成本和限制

本项目房间最多 12 人，最近记录只保留 50 条，单个 room 文档体积在当前 MVP 范围内可控。

后续如果需要长期保留大量记录，再考虑把历史记录归档到只读分页集合；当前阶段不引入额外业务表。

## 6. 验收

人工验收：

1. A 创建房间并停留在房间页。
2. B 加入房间后，A 页面自动出现 B。
3. 开启加入确认时，房主端自动出现 pending 卡片。
4. 房主同意或暂不加入后，申请人页面状态同步变化。
5. 房主给成员加扣分后，其他在线成员页面自动更新分数和记录。
6. 批量记分后，所有在线成员页面更新受影响成员和最近记录。
7. 积分转移后，所有在线成员页面更新相关成员、公共积分和最近记录。
8. 撤销后，所有在线成员页面按反向变化量更新。
9. 关闭房间后，所有在线成员页面进入只读状态。
10. 离开房间页后监听关闭，重新进入后重新建立监听。

自动检查：

1. 项目规定的 `node --check`。
2. 模板内容检查。
3. 高风险文案检查。
